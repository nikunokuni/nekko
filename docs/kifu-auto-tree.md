# 棋譜の一括読み込みと分岐地点の自動提案 ―― 設計メモ

作成 2026-08-01 / ステータス: **設計中（未着手）**

「大量に自分の棋譜を読み込んで、分析して、自動でツリーを作る」という着想を、
アプリの目的に照らして具体化したもの。あわせて、既存の「棋譜ノードから複数の分岐を
作ると横並びになる」問題を扱う。両者は**同じ原因から出ているので同じ手で治る**。

---

## 0. 目的の確認

| | |
|---|---|
| ターゲット | 1級くらいの人 |
| 目的 | **序中盤の戦法の使い分けができるようになる**（相手の出に合わせて有効な方針を選べる） |
| ツリー作り | 目的ではなく**手段** |
| 棋譜の読み込み | 研究ノート書きを**助ける補助機能**。主役ではない |

出発点になった実感（旧バージョンを自分で使ってみて）:

1. **どこで分岐させればいいかが分かりにくい** → 自動生成でベースを作りたい
2. **棋譜が1つだと相手の出方も1つしかなく、他の分岐の必要性が見つけにくい**
   → 複数の棋譜を見て、よりよい分岐地点を見つけたい

---

## 1. 最初の着想に含まれていた前提の棚卸し

「大量に読み込む → 分析 → 自動でツリー」を、いったん疑ってから組み直した記録。

| # | 前提 | 実際 |
|---|---|---|
| ① | 棋譜からツリーが作れる | ねっこのノードの中身は**ほぼ全部が主観**（`myApproach` / `usageLevel` / `winRate` / `likeLevel` / `studyMemo` …）。棋譜から埋まるのは分岐の骨格だけで、価値の中心は1文字も埋まらない。骨格を大量生成すると**空ノードの山＝負債**になる |
| ② | 「分析」ができる | エンジンは無く、評価値は手入力（`20260718_add_turn_evaluation.sql`）。さらに `kifuParser.js` は `KIF_END_WORDS` で終局を検出して**打ち切るだけ**で勝敗も対局者も保存していない。現状できるのは評価ではなく**集計**、それも勝敗を持っていないので今は集計すらできない |
| ③ | 大量に読み込ませる | 大量の棋譜を持っているのは開発者だけ。**新規ユーザーの棋譜は0局**。オンボーディングには効かない |
| ④ | 自動生成＝新規ツリー作成 | 履歴に `daa0bac 新規ツリー作成時の棋譜インポートを削除` がある。**一度その方向を試して外している** |
| ⑤ | 手間を減らすことが価値 | 手で並べ替え、自分の言葉で書く過程そのものが商品。そこを自動化すると面倒ではなく**楽しみが消える** |

**結論**：作るのは「ツリーの自動生成」ではなく **「分岐地点の推薦」**。
ツリーを完成させるのではなく、**どこで分けるべきかだけを教えて、書くのは人間**。

---

## 2. 分岐地点の自動提案

### 考え方

複数局を重ねたとき、**相手の手が割れた地点こそが分岐地点**。
これは上記の実感 1・2 の裏返しであり、そのまま仕様になる。

### アルゴリズム

1. N局を**局面ハッシュ列**（`board` + 両持ち駒 + 手番）に変換する
2. 同一局面をマージした**木（トライ）**を作る
3. 各局面で「**相手の**次の手」の種類と出現回数を数える
4. スコア = 相手の手の割れ具合 × その局面への到達局数
   （勝敗を持てるようになったら「そこから先の勝率の落差」を掛ける）
5. 上位K個を「ここで分岐を作りませんか？」として提示

### 仕様として効く3つの制約

- **相手の手の分岐だけを候補にする。**
  目的が「相手の出に合わせて方針を選ぶ」なので、分岐の原因は相手側に置く。
  ねっこはこれを既にデータモデルで持っている ―― `situation`（相手の戦法）と
  `myApproach`（自分の戦法）。
  **「相手の出方＝ノードの分かれ目、自分の方針＝ノードの中身」**とすると、目的と画面が一致する。
- **先手番と後手番は別ツリーにする。** 混ぜると意味が壊れる。
- **到達局数が2局未満になったら打ち切る。**
  実戦の棋譜は30〜40手も進めば局面が重ならなくなるので、
  **この打ち切りが自然に「序中盤」を切り出す**（狙いと機構が一致している）。

### 出力の規模感

50局読んで出てくるのは数百ノードではなく**分岐点5〜10個**。
これが「使い分けを覚える」のに必要な情報量。

### 提示の仕方

**ツリーに直接生やさない。**「取り込み候補」として出し、1件ずつ採用／破棄させる。
人間が捨てられる設計なら精度が低くても機能として成立する。
逆に直接生やすと、精度が高くても「掃除が面倒」で嫌われる。

## 3. 分岐①②が横に並ぶ問題

### 症状

ノードに棋譜を読み込み、途中で分岐①を作り、①より後ろで分岐②を作ると、
**①と②がマインドマップ上で横に並ぶ**。
直感的には主根（幹）と側根 ―― 幹が縦に伸び、側根が別々の高さから出る形。

### 原因

`src/screens/MindMapScreen.jsx` の `layoutTree`（57行目〜）:

```js
positions[id] = { x: xCounter * (NODE_W + 16), y: depth * (NODE_H + 40) };  // 71行目
```

**y座標が `depth` だけで決まる。** ①も②も同じ親の `childIds` なので同じ depth → 同じ y → 横並び。

さらに 80行目:

```js
const midX = ((startX + endX) / 2) * (NODE_W + 16);  // 親は子全体の中央
```

親が子の中央に来るため、**幹がまっすぐ下りずジグザグする**。

必要な情報は既に持っている。`branch_from_move_index`（`20260613_add_branch_from_move_index.sql`）に
「何手目から分岐したか」が入っている。**レイアウトがそれを無視している**だけ。

### 本質

**1ノードが棋譜100手ぶんの「時間」を抱えているのに、地図上では点1つ。**
だから10手目の分岐と25手目の分岐の前後関係を表現する場所がない。
「主根と側根」という直感は正しく、**幹には長さが要る**という指摘になっている。

### 3つの解き方

| | 内容 | 見た目 | コスト | 評価 |
|---|---|---|---|---|
| **A** | `childIds` を `branchFromMoveIndex` 順に並べ替えるだけ | 横並びのまま（順序だけ正しい） | 数行 | 症状に触れない |
| **B** | 棋譜ノードを**手数に比例した縦長の棒**として描き、側根を該当手数の高さから生やす | 理想形そのもの | 中〜大（可変高さ・エッジ接続点・ドラッグ判定 `535行目付近` を全て直す） | 見た目は正解だが、幹の中身が1ノードのままなので研究が書けない |
| **C** | **幹を分岐地点で自動分割し、幹ノードの列にする** | 主根＋側根 | 中 | ◎ **推奨** |

### 推奨：C

```
幹1（初手〜10手）──┬─ 側根：相手が△8四歩なら…
                    │
幹2（11〜25手）─────┼─ 側根：相手が△3三角なら…
                    │
幹3（26手〜）───────┴─ 側根：…
```

`handleBranchRangeFromKifu`（`src/App.jsx:346`）が既にやっている「範囲切り出し」を、
**分岐点で自動的にやる**だけ。新しい概念を持ち込まない。

Cが効く理由:

- **横並び問題が構造で消える。** 深さ＝手数の進行になるので①と②は自然に上下に並ぶ
- **幹ノードにも研究が書ける。** Bだと幹は1ノードのままで「この10手の組み立ての狙い」を
  書く場所がない。Cなら各セグメントに `openingFocus` や `studyMemo` が書ける。
  **研究ノートとしてはここが決定的な差**
- **自動生成と同じ機構。** 分岐点検出 → セグメント分割は同じ処理。片方を作ればもう片方も動く

**分割の粒度に注意**：分割しすぎると1手1ノードになり、ただの棋譜再生に退化する。
**実際に分岐が起きた点だけで切る。** 50局で分岐点5つなら幹は6ノードが上限。

### Cに必要な小さなレイアウト修正

Cだけだと、幹ノードが「幹の続き＋側根」の2子を持つため 80行目の中央揃えでジグザグする。

```js
// 幹ノードは、幹の続き（＝先頭の子）の真上に置く
const midX = isTrunk ? positions[children[0]].x
                     : ((startX + endX) / 2) * (NODE_W + 16);
```

幹の続きを常に `sortOrder` 先頭に置けば、**幹は x が揃った一直線の縦列になり、側根が右へ広がる**。
これが主根と側根そのもの。10行程度で、棋譜を持たない既存ツリーにも
「本筋が縦に通る」効果が出る。

## 4. 実装順

1. **レイアウト修正だけ先に入れる**
   （幹を真下に固定＋`branchFromMoveIndex` 順に整列）。
   10行程度で**主根・側根の見え方が想像通りかを即座に確認できる**。
   ここが違うと以降の設計が変わるので最初に潰す。影響範囲は `layoutTree` のみ
2. **`kifus` に勝敗・対局日・手番を追加**し、`kifuParser.js` でヘッダと終局を拾う
   （現状は検出して捨てている）。以降すべての土台
3. **局面ハッシュ＋トライ構築 → 分岐点検出**。
   純粋関数として書き、`treeOps.js` と同じ思想で `test-harness` からテストする
4. **分岐点の提案UI**（候補として提示 → 1件ずつ採用）
5. 採用時に**幹セグメント分割＋側根ノード生成**。
   `situation` に相手の指し手から推定した戦法タグを仮入力する

### 必要なスキーマ変更（`supabase/migrations/` に追加）

- `kifus`: `result`（勝敗）/ `played_at`（対局日）/ `my_side`（自分の手番）
- `kifus` または `nodes`: **局面ハッシュ列**（照合用の軽量列）。
  `fetchAllMyNodes` は重さを理由に `kifu` を除外しているので、
  ハッシュだけを別カラムで軽く持てる形にする
- `nodes` に列を追加する場合は `copy_tree` RPC の列リストも併せて更新すること

## 5. 派生アイデア（後回し・記録のみ）

- **自動接続**：棋譜取り込み時に局面ハッシュで既存ノードと照合し、
  「この棋譜、22手目まで〈四間飛車→美濃囲い〉のノードと同じ進行です」と提案する。
  自動生成ではなく自動接続なので、「書く道具」のまま面倒だけが消える
- **自己申告と実測のズレ**：`usageLevel` / `winRate` は自己申告値。
  実戦の集計と突き合わせると、エンジンなしでも刺さる事実が出せる。
  「頻度4と書いたノード、直近30局中3局です」「勝率7割と申告、実測4割です」
  「保存済み18局がどのノードにも載っていません（＝未研究の穴）」。
  **主観データを持つねっこにしか出せない情報**。前提として 4-2（勝敗の保存）が要る

## やらないこと

- エンジンによる評価・最善手の提示（ねっこの目的から外れる）
- 棋譜から**ノードの中身**を自動生成すること（主観の記録がこのアプリの価値の中心）
- 自動生成物をツリーへ直接書き込むこと（必ず候補として提示し、人間が採用する）
- 終盤の分岐（到達局数の打ち切りで自然に序中盤に限定される）
