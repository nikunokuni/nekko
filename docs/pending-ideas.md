# 保留にした案の記録

検討したが「今はやらない」と決めた案を残す場所。
**何を保留にしたか**より**なぜ保留にしたか／どうなったら着手するか**が本体。

同じ相談は忘れた頃にまた出てくる。そのとき最初から考え直さずに済むように、
そのときの判断材料（何が分かっていて、何が分かっていなかったか）ごと残す。

## 1. 表示項目の設定を「ツリーごと」にできるようにする

- 状態：**保留**
- 起票：2026-08-06
- 関係する実装：`src/components/TsuikaVisibilityModal.jsx` / `src/rewards.js` の
  `isTsuikaVisible` / `src/data.js` の `TSUIKA_ITEMS`

### いまの形

ノード編集画面に出す項目（合流・一言コメント・ミニ盤面・評価値・志向・
序盤の意識・頻度・勝率・好き度・研究メモ）のON/OFFは、
**利用者に1セットだけ**持たせている（`profiles.tsuika_visibility`）。

置き場所は「ついか」見出しの歯車。もとは設定画面のアコーディオンの中にあったが、
「入力欄が多い」と感じる場所（ノード編集画面）から
ツリー一覧 → 設定 → アコーディオン と3手離れていたため移した。

### 出た案

> 設定画面とついかの歯車の両方に置いて、
> **設定画面＝新規ツリーの既定値／ついかの歯車＝そのツリーだけの設定**にする。
> ツリーごとに粒度が違う。研究メモを書きたいツリーもあれば、
> 評価値をがっつり書きたいツリーもあるかもしれない。

### 保留にした理由

**ニーズ（ツリーごとに粒度が違う）は否定していない。**
保留にしたのは「既定値＋個別」という**解き方**のほうと、
そもそも今その痛みが出ているのかがまだ分からないため。

1. **既定値は、変えても何も起きない設定になる。**
   設定画面でトグルを倒しても、開いているツリーは何も変わらない。
   効くのは「これから作るツリー」だけで、フィードバックが返ってこない。
   利用者から見ると「設定したのに効かない」と区別がつかない。

2. **見た目が同じ設定が2か所に並ぶ。**
   同じ10項目・同じトグル・同じ見出しで、違いは
   「今のツリーに効く／これから作るツリーに効く」だけ。
   その差は画面に書けない（書いても読まれない）。
   設定画面から歯車へ寄せた理由がそのまま逆流する。

3. **いちばんやりたい「まとめて変える」ができない。**
   「やっぱり評価値は全部のツリーで出したい」と思ったとき、
   既定値方式では既存ツリーを1つずつ開いて直すことになる。
   全体設定が欲しくなる動機の本体はそこなのに、既定値はそこを助けない。

4. **設定がツリーに合っていないときの痛みが、そもそも小さい。**
   表示OFFはデータを消さない。OFFにしなくても書かなければいいだけなので、
   合っていない状態のコストは「空欄が1つ余分に並ぶ」程度。
   作り込むコストに対して痛みが釣り合っているかがまだ分からない。

### やるならこの形（既定値方式は採らない）

**全体設定は1つのまま。歯車の中に「このツリーだけ」の上書きを足す。**

```
┌─ 表示する項目 ──────────────┐
│  [ すべてのツリー | このツリーだけ ]  │  ← ここだけ追加
│  ────────────────────────  │
│  合流             [ON]           │
│  一言コメント      [ON]           │
│  ...                             │
└──────────────────────────┘
```

- 既定は「すべてのツリー」＝**今と完全に同じ挙動**。既存利用者は何も変わらない
- 「このツリーだけ」に切り替えた瞬間、**今の全体設定をコピーして持たせる**
  （白紙から選び直させない）
- **「すべてのツリーに戻す」を必ず置く。** 戻せないと
  「なぜこのツリーだけ違うのか」が分からないまま詰む
- 上書き中のツリーは、**ついか見出しに小さく印**を出す
  （印が無いと、別のツリーを開いたとき「設定が飛んだ」と読まれる）
- **入口は歯車の1か所のまま。設定画面には戻さない**
- **「みんなで編集」ツリーでは、オーナーの上書きをゲストに適用しない。**
  他人の好みで自分の入力欄が消えるのは、機能が壊れたようにしか見えない。
  ゲストは常に自分の全体設定、と決め打つ

### 実装の見積り（2026-08-06 時点のコード）

| 作業 | 量 |
|---|---|
| `trees.tsuika_visibility jsonb null` を追加 | migration 1本。**`null` = 全体設定を使う**ので既存ツリーの移行は不要 |
| `isTsuikaVisible(key)` にツリーの上書きを渡す | 読む場所は `NodeDetailScreen.jsx` の10行と歯車モーダルだけ。1画面に閉じている |
| モーダルに切り替えタブと「戻す」を足す | `TsuikaVisibilityModal.jsx` の中で完結 |

**あとから足せる形になっている**（`null` = 全体設定、で既存ツリーは無傷）ので、
今やらないことによる手戻りは無い。

### 再検討の合図

次のどれかが起きたら着手する。

- **「このツリーでは評価値（研究メモ）を出したい」と思った具体的なツリーが実際に出てきた。**
  そのとき、**どの項目が割れたのかを記録する** ―― 本当に割れるのは10項目のうち
  1〜2項目かもしれない。全項目を切り替え可能にする必要があるとは限らない
- 全体設定を、ツリーを開くたびに行ったり来たり切り替えている自分に気づいた
- 終盤研究・序盤研究のように、**性格の違うツリーを意図的に作り分けはじめた**

逆に、しばらく使っても全体設定を一度も触らないままなら、この案は**破棄**でよい。

## 2. ツリー／ノードのテンプレートをアプリ側で用意する

- 状態：**保留（アプリ側テンプレートは作らない方向。見本ツリーで代替する）**
- 起票：2026-08-06
- 関係する実装：`App.jsx` の `handleNewTree` / `kifuBranching.js` /
  `data.js` の `BOARD_TEMPLATES` / `db.js` の `copyTree`

### いまの形

新規ツリーを作ると、ルートの下に「居飛車」「振り飛車」「とりあえず」の
3つだけができる。中身はほぼ空。

### 出た案

> アプリ側でツリーのテンプレートをいくつか用意し、新規作成時に選ばせる。
> ノードも同様。ただしノードは呼び出し機能があるので、
> お気に入りノードをテンプレート用ツリーに溜めておけば利用者側で実現できる。
> アプリ側で持つか、公開ツリーとして置いておくかの選択肢がある。

### 保留にした理由（アプリ側で持つ案について）

1. **「やらない」と既に決めてある判断に当たる。**
   `kifuBranching.js` 冒頭に「定跡表を持たせて『教科書的にはこう』と言わせると、
   アプリが知識を主張することになり補助の域を超える」と書いてある。
   骨格だけ・中身が空でも「この相手が重要だ」という主張は入る。
   誰と当たるかはその人の実戦で決まるので、アプリには決められない。

2. **その役割は「分岐の候補」がすでに持っている。**
   しかも本人の棋譜から生成する形で。同じ場所に2つの提案が並ぶことになり、
   汎用のほうが必ず劣る（当たらない相手の枝が混ざる）。

3. **空の枝が並ぶと「宿題」になる。**
   想定棋力（1級前後）では、テンプレートの枝の大半はまだ当たっていない相手。
   未着手の空ノードが並ぶ状態は、「とりあえず」を作ったときの判断
   （置き場所を決めずに放り込める逃げ道を用意する）と逆を向く。

4. **メンテナンスが終わらない。** 戦法は無数にあり、揃えるほど
   「自分の戦法が無い」人が出る。中身を充実させるほど棋書の劣化コピーになる。

### 盤面テンプレートとの違い（線引きの実例）

`BOARD_TEMPLATES`（平手・ゴキ中）はアプリが持っていて、これは正しい。

- **盤面テンプレート＝事実。**「ゴキゲン中飛車の初形はこの駒組み」は
  誰も否定しない。どう指すべきかを主張していない
- **ツリーテンプレート＝主張。**「この相手を想定して、この順で分けるべき」

この線が、盤面は持ってよく、ツリーは持たないほうがいい理由。

### やるならこの形（アプリではなく人が主張する）

**見本ツリーを公開ツリーとして置く。仕組みはすでに全部ある**
（公開・`copy_tree`・プレビュー・いいね）。実装ゼロで始められる。

- `niku` で「見本」ツリーを1〜2本、**中身まで書いて**公開する。
  空の骨格を配ると「埋めなきゃ」になるが、書かれた完成形は
  「こう書けばいいのか」が伝わる。狙い・気を付けること・いつ使う が
  実際に埋まっている1本のほうが、空の10本より効く
- 見つかる導線を1つだけ足す。ツリー一覧の空のとき
  （`TreeListScreen.jsx` の「ツリーがまだありません」）に「見本を見る」を添える
- **新規作成にテンプレート選択画面は挟まない。** 今は名前を入れて即マップ。
  選択肢を挟むと、一番大事な最初の瞬間に「どれを選べばいいか分からない」で止まる

### ノードのテンプレートは作らない

呼び出し（`NodeRecallModal`）は全ツリーを横断するので、
「テンプレート置き場ツリー」を作って溜める運用がそのまま成立する。
足すとしたら機能ではなく紹介（呼び出しモーダルに一言）。

ただし**その運用が実用になるかは、呼び出しモーダルの使い勝手次第**。
現状は検索欄だけで並べ替えが無く、全ノードが作成日の新しい順に同列で並ぶ。
→ 4.（ノードのお気に入り）と一緒に考えること。

### 今の「居飛車／振り飛車」は残す

定跡の主張ではなく分類の2大区分でほぼ普遍。
加えて `situation` タグが入っていて、分岐の候補の照合に効いている。
中身が空なのは欠陥ではなく設計どおり（事実はアプリ、理由は人間）。

### 再検討の合図

- 見本ツリーを公開してみて、**コピーされるのに使われない**（コピー後に
  中身が育たない）なら、問題は入口ではなく別の所にある
- 「自分の戦法のツリーをどう始めればいいか分からない」という声が、
  棋譜をためたあと（＝分岐の候補が出るようになったあと）にも残るかどうか

## 3. 「使い方のヒント」をまとめて読む画面を設定に作る

- 状態：**保留（豆知識が溜まってから）**
- 起票：2026-08-06
- 関係する実装：`SettingsScreen.jsx` / `onboarding.jsx` の `ONBOARD_MESSAGES` /
  `NodeDetailScreen.jsx` の `BRANCH_TIPS`

### 何の話か

ねっこは機能が多く、奥にある使い方（呼び出しでテンプレート運用をする、
まとめノードで章立てする、など）は気づかれにくい。
**それをまとめて読める場所が無い。**

もともとは「使い方説明をトロフィーにする」案から出た。
トロフィー案のほうは採らないと決めている（下記）。

### トロフィーにしない理由

今の41個は **`desc` = 機能の紹介文 ／ `check` = その機能を使ったか**
という契約で揃っている。使い方の工夫（例：「テンプレートという名前の
ツリーを作る」）を混ぜると3つ壊れる。

1. **判定が名前の一致になる。** アプリが特定の文字列だけを正解と主張する
   ことになり、「定型」「よく使う形」で同じことをした人は永久に取れない
2. **狙う行動と報われる行動がズレる。** してほしいのは「よく呼び出す
   ノードを集めて再利用する」で、それは既に「使い回す」が拾っている。
   新しいバッジが報うのは*命名*だけ
3. **未獲得バッジが宿題リストになる。** トロフィー画面は「何をしたか」の
   記録。「まだやっていない使い方」を混ぜると、ロックされた札の列が
   「できていないことの一覧」に変わる。
   「次に調べること」→「次にやりたいこと」の改名と同じ線

### まずやること（画面を作る前に）

**豆知識は、それが必要になる場所にその場で置く。** 実例が既に3つある。

| 場所 | 形 |
|---|---|
| 子ノードの「ヒント」 | `BRANCH_TIPS` 10項目。手が止まったときに開くモーダル |
| 棋譜ライブラリの空状態 | 「棋譜ファイルが無いときは、盤に並べて入力する」 |
| 画面ごとの初回トースト | `ONBOARD_MESSAGES` |

例：テンプレート運用の豆知識なら、置き場所は
**呼び出しモーダルのツリー絞り込みのそば**（まさにそこで使う知識）。

### 画面を作るならこの形

- 設定の中に「使い方のヒント」を1画面。オンボーディングの再表示の隣
- 中身は**その場に置いた一言の再掲**（＝出どころは1か所にする）。
  ここにだけ書かれた知識を作ると、必要な場面では誰も読まない

### 再検討の合図

- **その場に置いた豆知識が5個くらい溜まった。**
  1個のために画面を作ると、その画面自体が開かれない
- 「機能が多くてどこに何があるか分からない」が、
  オンボーディングを見直しても解消しない

## 4. 将棋エンジンを内蔵する（評価値・評価値グラフ）

- 状態：**保留（内蔵はやらない方向。評価値の「取り込み」なら別途やれる）**
- 起票：2026-08-06
- 関係する実装：`kifuParser.js` / `kifuFields.js` の `sourceText` /
  `nodeFields.js` の `evaluation` / `NodeDetailScreen.jsx` の `BRANCH_TIPS`

### 出た案

> 将棋エンジンを入れて、盤面の評価値と棋譜の評価値グラフを出す。
> ノードの分岐点も見つけやすくなる。
> アプリの原則からは外れるが、原則を変えてねっこだけで完結させるのはどうか。

### まず前提の整理 ―― 原則は思ったより外れていない

原則が禁じているのは**評価値というデータ**ではなく、
**アプリが良し悪しを断定すること**。実際、評価値は既にコードに入っている。

- `nodeFields.js` に `evaluation` 列（手入力）
- `BRANCH_TIPS` に「評価値が大きく動いた手（勝負の決め手になった悪手）」
  ＝ **アプリは既にこの観点を勧めている**（他のソフトで調べる前提で）

つまり線はここに引ける。

- ○ **「ここを見てみては」と指す**（評価値が動いた手を分岐の候補として出す）
- × **「この手は悪手です」と言う**（形勢判断の断定）

やりたかった「分岐点を見つけやすくする」は前者なので、
**原則を変えなくても実装できる**。

### 内蔵しないと決めた理由

1. **時間。** 内蔵は3〜6週間＋継続運用。その時間は傾向分析・分岐候補・
   ツリー作りに使える。実際、「次にやりたいこと」「しおり」「タグ引き継ぎ」は
   全部合わせて1週間かかっていない
2. **比較される土俵が変わる。** 積んだ瞬間ねっこは「解析ソフト」の棚に並び、
   精度・速度・評価関数の新しさで必ず負ける。いま立っているのは
   **競合がいない棚**（実戦の傾向から自分のツリーを作る）
3. **運用が発生する。** 今は静的ホスティング＋Supabaseで運用ほぼゼロ。
   エンジンは配信・メモリ・端末差の面倒を毎回連れてくる
4. **級位者前提だと効きが小さい。** 1級前後で同じ局面が再現しない帯では、
   1手ごとの評価値より「どの戦型でどう負けているか」が勉強を動かす。
   それは既に kifuStats がやっている

### 使い方の位置づけ（この相談で決まったこと）

> **解析ソフト（または解説動画）を見ながら、ねっこにメモしていく。**

ねっこは**解析する側ではなく、受け取って残す側**。
この線引きは、エンジンだけでなく他の判断にも効く
（アプリ側テンプレートを持たない＝2.、と同じ向き）。
利用者は既に他のソフトで解析している。ねっこに要るのは
**解析する能力ではなく、解析結果を受け取る口**。
口を作れば、エンジンの精度は常に「他のソフトの最新版」に追随する。

### 着手前に潰す落とし穴（内蔵を検討する場合）

1. **ライセンス。** 主要な国産エンジン（やねうら王系）は GPLv3。
   WASM で配布するとリンク扱いになり、**ねっこ全体のソース公開義務が
   発生しうる**。このリポジトリには現在 **LICENSE ファイルが無い**。
   技術判断ではなく「このアプリをどう公開するか」の決断になる
2. **COOP/COEP。** マルチスレッド（SharedArrayBuffer）を使うと厳しい
   ヘッダが要り、**Google Fonts の読み込みが通らなくなる可能性**がある
   （自前配信への切り替えが要る）。シングルスレッドなら回避できるが遅い
3. **数字の裏取り。** 評価関数ファイルの大きさ・WASMビルドの入手性は
   実物で確認すること。下の見積もりは記憶ベースで、鵜呑みにしない

### コスト見積り（2026-08-06 時点）

**A案：評価値付きKIFを取り込む（エンジンなし）… 2〜3日**

将棋ウォーズ・ShogiHome・水匠などが出す KIF は、コメント行に評価値を
持つことがある（形式はソフトごとに違うので調査が要る）。
**`source_text`（KIFの原文）をDBに保存済みなので、既に取り込んだ棋譜も
遡って読み直せる**（取り込み直し不要）。

| 作業 | 見積 |
|---|---|
| `kifuParser.js` にコメント行の評価値読み取り（形式調査込み） | 0.5〜1日 |
| `kifus.evals` 列（台帳1行＋migration 1本） | 1時間 |
| 評価値グラフ（SVG。`mapLayout.js` と同じ純粋関数方式でテスト可能） | 半日 |
| **評価値が大きく動いた手を、しおり候補として自動で出す** | 半日 |
| テスト（unit＋E2E） | 半日 |

最後の行が本命。しおり機能と直結して「探す作業」がほぼ消える。

**B案：WASMエンジンを内蔵… 3〜6週間＋継続運用**

エンジン選定・ライセンス確認／評価関数ファイルの配信とPWAキャッシュ／
COOP/COEP と外部リソースの見直し／Worker 経由の USI 実装／
解析結果の保存とバージョン管理／モバイル実機検証。

### 段階の切り方（やるとしても順番がある）

1. **評価値を読むだけ**（A案）→ グラフ＋しおり候補の自動化
2. ここで満足するか見る（**たぶん満足する**）
3. 足りなければ、単一局面だけ・短時間・シングルスレッドで試す
4. それでも足りなければフル内蔵（＝ライセンスの決断）

**1は捨てる部分が無い。** エンジンを積む場合でも、評価値の保存形式と
グラフはそのまま使える。

### 再検討の合図

- **手元のKIFに評価値が入っているかを先に確認する。**
