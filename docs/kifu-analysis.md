# 棋譜分析とツリー自動生成の設計メモ

大量の棋譜から勝てる傾向を抽出し、最終的にツリーの下書きを自動生成するまでの
設計と、そこに至る判断の記録。実装の途中経過ではなく「なぜそう決めたか」を残す。

- 対象棋力：1級前後（同一局面がほとんど再現しない帯）
- 最終更新：2026-08-01
- 実装ブランチ：`claude/kifu-analysis-win-patterns-45kx0e`

---

## 1. 何のための機能か

ねっこの目的は3つ。

1. 相手の呼吸に合わせた自分の方針をまとめられる
2. 自分の強みと弱みといった棋力の現在地がわかる
3. 勉強の方針や対局中の方針がわかり、棋力向上に役立つ

このうち **2 は機械が数字で出せる**。1 と 3 は人間が言葉で書く。
この線引きが機能全体の設計を決めている。

> **機械は「事実と数字」、人間は「理由と狙い」。**

統計はすべてコードで計算する。LLM に盤面を読ませて形勢判断や指し手の
良し悪しを言わせることはしない（盤面認識が弱く、それらしい嘘を書くため）。
LLM の担当は「数字を言葉にする」ことと「名前を付ける」ことに限定する。

## 2. ノードを分ける理由は4つしかない

実戦の分岐場面を分類すると、次の4つに収まる。

| # | 分岐の理由 | 対応する既存フィールド | 検出に必要なもの |
|---|---|---|---|
| ① | 有力手が複数ある（志向の選択） | `orientation`（攻め/受け/バランス） | エンジン（MultiPV） |
| ② | 自分が大きく評価値を落とした | `caution`（注意）＋ `evaluation` | エンジン |
| ③ | 相手が大きく評価値を落とした | `aim`（ここでの狙い）＝罠 | エンジン |
| ④ | 相手が違う戦法を使ってきた | `situation`（相手の戦法） | 特徴抽出のみ |

この4分類は、手で使い込んで育てた既存のノード項目とほぼ一対一で対応していた。
偶然ではなく、実際の分岐理由が項目設計に現れていたということ。
**この4分類を検出ロジックの仕様そのものとする。**

### 却下した案：全指し手のトライを作って頻度で刈る

機械にとって作りやすいだけで、ノードに意味がない。
手順で分岐させると、狙い・注意・宿題が埋まらない空ノードだらけになる。

### 最重要の原則：1回の悪手は傾向ではない

1級帯なら1局に大悪手が5〜10回ある。全部ノードにしたら1局で破綻する。

> **繰り返している悪手だけが「傾向」。単発のミス指摘は既存の棋譜解析ソフトの仕事。**

したがって ②③ のノード化条件は「**同じ特徴グループ・同じ手数帯で N局以上 発生**」。
100局読ませる意味はここにしかない。

なお ③（相手の悪手）は ②（自分の悪手）より価値が高い可能性がある。
「この形にすると相手はよくここで間違える」は勝ちに直結し、`aim` に書く内容そのもの。

### 縦と横の対応

- **④ 相手の戦法** → 兄弟ノード＝ツリーの**横**の広がり
- **①②③ 判断** → その戦法ノードの子＝**縦**の深さ

## 3. 局面のキーは「丸める」のではなく「階層化する」

1級帯では20手も進めば完全一致はほぼ出ない。だが**局面同士の距離を測って
ファジーにまとめる方式は採らない**。理由は精度ではなく説明可能性。

- 「なんとなく似た局面」でグループ化されても将棋指しは納得しない
- 外れたときに理由が言えない（ブラックボックスになる）

代わりに、局面から**名前の付く特徴**を抜き出し、粗いキーから細かいキーまで
すべての粒度で同時に集計する。

```
L1: 相手の戦法
L2: + 自分の戦法            ← 自分も常に同じ戦法とは限らないので必須
L3: + 自分の囲い
L4: + 相手の囲い
```

集計は全レベルで回し、**母数が閾値を超える一番細かいレベルを自動採用**する。
細かい側が2つ以上に割れたときだけ置き換える（1つしかないなら情報が増えていない）。

これで「四間飛車には勝てているが、四間飛車＋穴熊には負けている」という
粒度の出し分けが自動で決まる。母数が足りなければ自動的に粗い側へ落ちるので
統計も壊れない（階層ベイズの縮約と同じ発想）。

**先手／後手は集計軸に入れず、絞り込み（フィルタ）で扱う。**
軸に入れると母数が半分になり、級位者の棋譜数では統計が成立しない。

### 歩の形は特徴に入れない

揺れが最大で、入れた瞬間に母数が割れて全部が「1局」になる。

### 「先発」と「対応」を分ける

同じ四間飛車でも、**自分から決めた**のか**相手を見てから合わせた**のかで
意味が正反対になる。相手の右四間飛車を受けるために振る、といったケースを
取りこぼさないため、飛車を振った順番から判定して独立の特徴として持つ。

- 自分の振り < 相手の振り（または相手が振らない）→ **先発**
- 相手の振りより後 → **対応**

これはねっこの目的1「相手の呼吸に合わせた方針」の直接の指標になる。

## 4. 生成するツリーの抽象度

**1手1ノードは採らない。** 100局から作ると数百ノードになり読めない。

採用するのは**2層構造**。

```
上層＝戦法ノード（④で分岐）… 「相手が四間飛車」「相手が中飛車」   10〜20個
  └ 下層＝判断ノード（①②③で分岐）… その形で繰り返す判断      各3〜7個
       └ 手順は kifu snapshots としてノードの"中"に持つ
```

> **ノードの分岐＝判断の分かれ目。手順はノードの中身。**

手順をノードの中に持つのは既存の範囲切り出し（`App.jsx` の
`handleBranchRangeFromKifu`）がやっていることそのままなので、
ノードモデルの変更は不要。既存の描画・再生・再切り出しUIがそのまま動く。

### 読める上限と、そのための上限ルール

**1ツリー 20〜40ノード・深さ3〜4** を目安にする。

- 1局から作るノードは最大2〜3個（最悪の悪手1つ、最大のチャンス1つ、志向の分岐1つ）
- ノード化には「N局以上で再現」を要求し、単発は捨てる
- 40ノードを超えたら母数の少ない順に切る

「もっと詳しく見たい」は自動生成では解決しない。ノードの中の棋譜を再生して、
気になった局面で自分で範囲切り出しして枝を伸ばす。
**自動生成は骨組みまで、肉付けは人間。** ねっこの「育てる」思想とも合う。

生成物は**下書きツリーとして別に作り**、利用者が取捨選択して本ツリーへ取り込む。
手で育てたツリーを機械が上書きすることは絶対に避ける。
手入力値と自動値の衝突を避けるため `source: 'auto' | 'manual'` 相当の区別を持たせる。

## 5. 自動生成でどこまで埋められるか

### 確実に埋まる（特徴抽出と集計だけで足りる）

| 項目 | 根拠 |
|---|---|
| `situation`（相手の戦法） | 特徴抽出そのまま |
| `myApproach`（自分の戦法） | 同上 |
| `usageLevel`（頻度） | 出現局数 → 1〜5 |
| `winRate`（勝率） | 集計値 → 1/3/5/7/9割 |
| `board` / `handSente` / `handGote` | 該当局面そのもの |
| `kifu` / `branchFromMoveIndex` | 区間切り出し |
| `turn`（手番） | 手数の偶奇 |

### ルールで下書きできる

- `status` … 頻出×低勝率 → `wip`（研究中）
- `label` … 「四間飛車 × 美濃」の機械生成。自然な戦法名は辞書かLLM
- `whenToUse` … 「相手が〇〇のとき」まで

### エンジン導入後に埋まる

- `evaluation`
- `orientation` … 候補手の分類が決まれば
- `commentTags` … 評価値推移から「逆転勝ち／逆転負け」は機械判定できる

### 埋められない ＝ ここがねっこの価値

`aim`（ここでの狙い）、`caution`（なぜ間違えたか）、`nextStudy`、
`likeLevel`、`memo`、`openingFocus`。

## 6. 実装状況

### 実装済み（エンジン不要の範囲）

| ファイル | 役割 |
|---|---|
| `src/kifuParser.js` | 指し手のパースに加え、対局者名・対局日・勝敗を読む |
| `src/kifuFeatures.js` | 盤面 → 飛車の筋・囲い（完成度つき）・角交換・振り時期 |
| `src/kifuStats.js` | 階層集計＋ウィルソン信頼区間 |
| `src/kifuAnalyze.js` | 上記3つのつなぎ役（先後の判定・勝敗の変換） |
| `src/screens/KifuInsightScreen.jsx` | 傾向画面（読み取り専用） |
| `supabase/migrations/20260731_add_kifu_result.sql` | kifus に対局情報の列を追加 |
| `test-harness/kifuAnalysis.test.mjs` | ユニットテスト（`node` で直接実行） |

主な決定事項：

- **勝敗のパースは指し手のパースと独立に行う。** 指し手側は読めない手が出た
  時点で打ち切る仕様なので、そこに相乗りすると壊れた棋譜から勝敗を取れなくなる。
- **既に取り込み済みの棋譜も `source_text`（原文）から後追いで解析できる。**
  取り込み直しは不要。傾向画面の「まとめて解析する」から実行。
- **特徴は取り込み時に計算して `features` 列へ保存する。** 集計のたびに全棋譜の
  `snapshots`（1局で数十KB）を取り直すと通信量が実用に耐えない。
- **駒落ちは集計から除外する。** 初期配置も先後の扱いも平手と異なる。
- 順位付けは生の勝率ではなく**ウィルソン信頼区間**。「2局2勝＝勝率100%」が
  上位に来るとランキングが意味を失うため。
- 「よく負ける」は勝率の低い順ではなく**取りこぼしている局数の多い順**。
  5局で勝率2割より、20局で勝率3割のほうが先に直すべき。

### 先後の自動判定と、対局者名の学習

大量取り込みを前提に、判定できないときの質問を
「先手？後手？」ではなく**対局者名そのもの**にした。

```
あなたは  [ にく ]  [ たろう ]  [ 分析しない ]
```

答えた名前は `profiles.kifu_player_names` に覚え、

1. 同時に読み込んだ他の棋譜をその場で再判定する（50局まとめて1回答えれば済む）
2. 次回以降は聞かれない
3. 傾向画面の「登録済みの名前で先後を判定し直す」で過去の棋譜へさかのぼれる

名前の照合に盤面は不要なので、まず軽い列だけで一致を調べ、
一致した棋譜だけ盤面を取りに行く。

### 主な定数（実データを見て調整する前提）

| 定数 | 値 | 意味 |
|---|---|---|
| `STRATEGY_SETTLE_PLY` | 40 | この手数までのうち、飛車が自陣にいた最後の筋を戦法とする |
| `CASTLE_OBSERVE_PLY` | 80 | 囲いはこの範囲で最も完成度が高かったものを採る |
| `EARLY_SWING_PLY` | 20 | ここまでに振れば「早い」 |
| `Z`（ウィルソン） | 1.0 | 約68%。1.96 だと母数10〜30で全部が判定不能になる |
| `minGames` | 3（3/5/10 で切替） | この局数未満のグループは「よく勝てる／よく負ける」の判定に載せない |

### 囲いの判定テンプレート（16種）

玉の位置が一致するものだけを候補にし、構成駒の一致率を完成度とする
（半分以上そろえばその囲いとみなす）。玉が5九のままなら「居玉」。
完成度が同じときは構成駒の多いほう（＝より発展した囲い）を採る。

すべて先手視点。後手は盤面を180度回して同じ表で判定する。

| 囲い | 玉 | 構成駒 |
|---|---|---|
| 居飛車穴熊 | 9九 | 9八香・8八銀・7九金・7八金 |
| 振り飛車穴熊 | 1九 | 2八銀・3九金・3八金 |
| ミレニアム囲い（居飛車） | 8九 | 8八銀・7九金・7七桂 |
| ミレニアム囲い（振り飛車） | 2九 | 2八銀・3九金・3七桂 |
| 矢倉 | 8八 | 7八金・6七金・7七銀 |
| 左美濃 | 8八 | 7八銀・6九金・5八金 |
| ボナンザ囲い | 7八 | 7七銀・6八金・5八金 |
| elmo囲い | 7八 | 6八銀・7九金・5九金 |
| 雁木囲い | 6九 / 7九 | 6七銀・7八金・5八金 |
| 舟囲い | 6八 | 7八銀・5八金・4九金 |
| 中住まい | 5八 | 3八金・4八銀・7八金 |
| 銀冠 | 2八 | 2七銀・3八金・5八金 |
| 高美濃 | 2八 | 3八銀・4七金・5八金 |
| 美濃囲い | 2八 | 3八銀・4九金・5八金 |
| 片美濃囲い | 2八 | 3八銀・4九金 |
| 金無双 | 3八 | 4八金・5八金・2八銀 |

ミレニアムは居飛車と振り飛車で左右が入れ替わるため、同じ名前で2つ登録している。
どちらの戦法で使ったかは「自分の戦法」の軸で別に分かれるので、名前は分けない。

玉の位置が同じ囲い同士（8八の矢倉／左美濃、7八のボナンザ／elmo、
2八の美濃系）は、完成度も構成駒数も同じになったときテンプレートの
並び順で決まる。基本形で出現頻度の高いものを先に置く。

副産物として**囲いの完成度**が出るので、「囲い切る前に攻められて負けている」
という級位者に頻出の負け筋を拾える。ただし片美濃のように金1枚でも完成形の
囲いがあるため、完成度の数字は画面に出さず、崩れているときだけ「組みかけ」と
添える（「67%」は「失敗」と読めてしまう）。

### 「とりあえず」ノード（置き場）

どこに置くか決まっていないものを入れておく場所。ツリー作成時に自動で1つ作る。

ルートを2本持たせる案もあったが、`rootId` / `is_root` は8ファイル74箇所から
参照され、マインドマップのレイアウトも単一ルート前提で組まれている。
置き場が欲しいだけならルート直下の普通のノード1つで足りるので、ツリー構造は
変えず `nodes.is_inbox` フラグだけを足した。

- マインドマップでは本体の枝の並びから外し、ツリー全体の**下に離して**置く。
  ルートとの線は引かない（上から下まで貫く線が本体と交差して読みにくくなるため）。
  位置で所属を示す。
- 普通のノードなので、整理がついたら通常のつなぎ替えで本体へ移せる。
- 棋譜プレビューの「ツリーの『とりあえず』に入れる」から、置き場所を決めずに
  棋譜をツリーへ送れる。この機能より前に作ったツリーには無いので、
  必要になった時点で `ensureInboxNode` が用意する。
- 普通のノードなので削除もできてしまう。消したあと戻す道が無いと詰むため、
  **ルートのノード編集画面の子ノード欄に「『とりあえず』を作る」を出す**
  （置き場が無いときだけ表示）。棋譜から送ったときも自動で作り直される。

## 7. 外部連携の選択肢

### 棋譜を大量に集める口（最大のボトルネック）

| 供給源 | 自動取得 | 備考 |
|---|---|---|
| **Lishogi** | ○ 公式API | 全対局を一括DL可。オープンソース。現実的な唯一の自動化先 |
| **floodgate / wdoor** | ○ アーカイブ公開 | 自分の棋譜ではないが「一般的な定跡統計」の母集団に使える |
| 81Dojo | △ 手動DL | |
| 将棋ウォーズ / 将棋倶楽部24 | **×** | 公式APIなし。スクレイピングは規約違反リスクが高く手を出さない |

ウォーズ勢には「ぴよ将棋でKIF書き出し → ねっこに読み込ませる」が現実解。
そのため**外部連携より先に複数ファイルの一括取り込みを作った**（実装済み）。

### エンジン（①②③に必須）

`YaneuraOu.wasm` などの USI エンジンをブラウザで動かす。

- マルチスレッド版は `SharedArrayBuffer` が必要 → COOP/COEP ヘッダ設定
  （`vercel.json` で可能だが外部リソース読み込みに影響）
- エンジン本体で数MBのダウンロード
- 全局面の解析は重いので「**統計で怪しいと出た局面だけ**」を解析する
- 局面キー → 評価値のキャッシュを持たせて再解析を避ける

エンジンなしでも「その局面以降ほぼ負けている＝勝率が急落する境界」で
敗着を近似できるので、必須になるのは ①②③ を作る段階から。

### LLM（Claude API）

**やらせて良いこと**：ノードの命名・戦法タグ推定、統計結果の日本語要約、
研究メモの下書き。

**やらせてはいけないこと**：盤面を直接読ませて形勢判断や指し手の良し悪しを
言わせること。

**必須の実装制約**：このアプリは Vite なので `VITE_` 付き環境変数は
ビルド成果物に丸見えになる。**API キーを絶対にクライアントへ置けない。**
Supabase Edge Function を1本立ててそこから叩く（Supabase は既に入っているので
追加インフラは不要）。コストはツリー1本の命名で数円程度。

## 8. 進め方

| Phase | 内容 | 状態 |
|---|---|---|
| 0 | 勝敗・自分の側・対局日のパース、一括取り込み | **完了** |
| 1 | 特徴抽出＋階層集計＋傾向画面（④と戦型別勝率） | **完了** |
| 2 | エンジン導入 → ①②③（繰り返す悪手・相手のミス・志向の分岐） | 未着手 |
| 3 | 2層ツリーの自動生成、LLM による命名 | 未着手 |

Phase 1 まではツリーに一切手を加えない読み取り専用なので、既存機能への
影響がない。ここで傾向抽出が本当に役立つかを確かめてから Phase 2 へ進む。

## 9. 未解決の論点

1. **②③の閾値（何点落としたら大悪手とみなすか）。**
   棋力帯に強く依存し、1級に400点を使うか800点を使うかで出てくるノードの
   数と質が変わる。実データを流して件数を見てから決める。

2. **候補手の性質分類（①のため）。**
   「敵陣方向へ動く＝攻め / 自玉2マス以内＝受け」といった単発の手の形からの
   分類は漏れが多い。エンジンの読み筋（PV）を使い「その手を選んだ後の3〜5手で
   自分の駒が敵陣に何枚入るか／自玉周りの守備駒が何枚増えるか」で測るほうが堅い。
   Phase 2 で実データを見ながら決める。

3. **囲いテンプレートの精査。**
   現在16種。升目は実戦の感覚に合わせて一度直してある。
   相居飛車の細かい囲い（矢倉の発展形など）はまだ「その他」に落ちる。

4. **最低局数の既定値。** 3 / 5 / 10 のどれが一番読みやすいか。
   これは ②③ の閾値決めにも直結する。
