# ツリー自動生成の構想メモ

利用者（ねっこの作者）の要望・違和感・疑問を整理し、それぞれに対する現時点の
方針と実装状況を対応づけたもの。技術的な判断の根拠は `docs/kifu-analysis.md`
に書いてあるので、こちらは「何をしたいか」と「それはできるのか」を並べる。

- 最終更新：2026-08-02
- 関連：`docs/kifu-analysis.md`（設計と判断の記録）

---

## 1. 前提

| 項目 | 内容 |
|---|---|
| ターゲット | 1級前後 |
| 目的 | 序中盤の**戦法の使い分け**ができるようになる（相手の出方に合わせて有効な方針を選ぶ） |
| ツリー作り | 目的そのものではなく**手段** |
| 大量読み込み×自動生成 | その手段をさらに助けるもの |

ねっこ本体の3つの目的：

1. 相手の呼吸に合わせた自分の方針をまとめられる
2. 自分の強みと弱み（棋力の現在地）がわかる
3. 勉強の方針・対局中の方針がわかり、棋力向上に役立つ

**2 は機械が数字で出せる。1 と 3 は人間が言葉で書く。** この線引きが全体の設計を決める。

> このアプリは「研究ノートを書く道具」であって、棋譜読み込みはそれを助ける機能。
> 棋譜解析ソフトになってはいけない。

## 2. 旧バージョンを使って分かった課題

| 感じた課題 | 自動生成でどう解くか |
|---|---|
| どこで分岐させればいいか分かりにくい | 自動生成でベース（骨組み）を作り、そこから育てる |
| 棋譜が1つだと相手の出方も1つ → 他の分岐の必要性に気づけない | 複数棋譜を横断して、より良い分岐地点を見つける |

つまり自動生成の役目は **「分岐地点の候補を提示すること」**。
ノードの中身（狙い・注意）を書くのは人間のまま。

## 3. 気になっていること：分岐が横に並ぶ

### 起きていること

棋譜を読み込んだノードから、

1. 棋譜の途中で分岐① を作る
2. ① より後の地点で分岐② を作る

すると **① と ② が横並び（同じ深さ）に配置される。**

### 原因（コード上の事実）

- `App.jsx` の `handleBranchRangeFromKifu` は、切り出し範囲がどこであっても
  **常に同じ親ノードの子**としてノードを作る（`createBranchNode(parentNodeId, ...)`）。
- `MindMapScreen.jsx` の `layoutTree` は `y = depth * (NODE_H + 40)` の
  素直な階層レイアウトなので、**兄弟は必ず同じ高さに並ぶ**。

つまり「分岐した手数」の情報（`branchFromMoveIndex` として保存はされている）が
配置に一切使われていない。

### 望ましいイメージ

マインドマップとしては **主根と側根**。

```
   [棋譜ノード]        ← 主根＝実際に指した流れ
        │
        ├── 分岐①      ← 30手目で分かれた側根
        │
        │
        └── 分岐②      ← 60手目で分かれた側根（①より下に出る）
```

同じ親から出ていること自体は正しい（①と②は「①を選んだ結果」ではなく、
同じ1局の別の分かれ目なので、②を①の子にするのは意味的に誤り）。
**直すべきは配置であって、親子関係ではない。**

### 取りうる案

| 案 | 内容 | 評価 |
|---|---|---|
| A | 子ノードの y を `branchFromMoveIndex` に応じてずらす | ◎ データは既にある。レイアウト関数だけの変更で済む |
| B | ② を ① の子にする | × 意味が変わる。「①を選んだ後に②」という誤読を生む |
| C | 主根を手数で複数ノードに割る | × ノード数が爆発し「2層構造」の方針と衝突する |

**案A を採る。** `layoutTree` に「同じ親の子は `branchFromMoveIndex` の順に
縦オフセットを加える」を入れる。棋譜を持たない通常のノード（`branchFromMoveIndex`
が無い）は今までどおり横並びのままにして、既存ツリーの見た目を壊さない。

## 4. 質問への回答

### Q1. 棋譜から「勝てる傾向」を見つけることは可能か？

**可能。すでに実装済み。**（`src/kifuStats.js` / `src/screens/KifuInsightScreen.jsx`）

- 局面から名前の付く特徴（相手の戦法・自分の戦法・囲い・角交換・振り時期）を抽出
- 特徴の組み合わせごとに勝率を集計
- 順位付けは生の勝率ではなく**ウィルソン信頼区間**（「2局2勝＝勝率100%」を排除）

### Q2. 大量の棋譜から「よく勝てる／よく出る／よく負ける」を抽出できるか？

**可能。実装済み。**

| 抽出軸 | 出し方 |
|---|---|
| よく出てくる | 出現局数の多い順 |
| よく勝てる | ウィルソン下限の高い順 |
| よく負ける | 勝率の低い順ではなく **取りこぼしている局数の多い順** |

「よく負ける」を局数で見るのは、5局で勝率2割より20局で勝率3割のほうが
先に直すべきだから。

### Q3. ツリーを一から育てる過程を、アプリにやってもらえるか？

**骨組みまでは可能。肉付けは人間。**

自動生成は「読み込んだ棋譜から、分岐すべき地点と戦法ノードの下書きを作る」まで。
狙い・注意・宿題を機械が埋めることはできないし、埋めようとすると嘘になる。

生成物は**下書きツリーとして別に作り**、利用者が取捨選択して本ツリーへ取り込む。
手で育てたツリーを機械が上書きすることは絶対に避ける。

### Q4. そのために何が必要か？

| 必要なもの | 用途 | 状態 |
|---|---|---|
| 棋譜の一括取り込み | 母数を稼ぐ | **実装済み** |
| 特徴抽出＋階層集計 | ④（相手の戦法）と勝率 | **実装済み** |
| USI エンジン（`YaneuraOu.wasm` 等） | ①②③（評価値が要る分岐） | 未着手 |
| Claude API（Supabase Edge Function 経由） | ノードの命名・統計の日本語要約 | 未着手 |
| Lishogi API | 棋譜の自動取得 | 未着手 |

- エンジンはブラウザで動かす。全局面を解析すると重いので
  **統計で怪しいと出た局面だけ**を解析し、局面キー→評価値をキャッシュする。
- LLM に**盤面を読ませて形勢判断や指し手の良し悪しを言わせることはしない**
  （盤面認識が弱く、それらしい嘘を書く）。担当は命名と要約に限定。
- Vite なので `VITE_` 付き環境変数はビルド成果物に丸見えになる。
  **API キーをクライアントに置けない** → Supabase Edge Function を1本立てる。
- 将棋ウォーズ／将棋倶楽部24は公式APIが無く、スクレイピングは規約違反リスクが高い。
  ウォーズ勢の現実解は「ぴよ将棋で KIF 書き出し → ねっこに読み込ませる」。
  だから外部連携より先に一括取り込みを作った。

## 5. ノードを分ける理由は4つしかない

実戦の分岐場面は次の4つに収まる、という整理。これを**検出ロジックの仕様そのもの**とする。

| # | 分岐の理由 | 対応するノード項目 | 検出に必要なもの |
|---|---|---|---|
| ① | 有力手が複数ある（攻め志向かバランス志向か等） | `orientation` | エンジン（MultiPV） |
| ② | 自分が大きく評価値を落とした | `caution` ＋ `evaluation` | エンジン |
| ③ | 相手が大きく評価値を落とした（＝罠） | `aim` | エンジン |
| ④ | 相手が違う戦法を使ってきた | `situation` | 特徴抽出のみ |

手で使い込んで育てた既存のノード項目とほぼ一対一で対応していた。
実際の分岐理由が項目設計に既に現れていたということ。

それぞれのノード詳細に、原因・見えなかった狙いを人間が書く。

### 最重要の原則：1回の悪手は傾向ではない

1級帯なら1局に大悪手が5〜10回ある。全部ノードにしたら1局で破綻する。

> **繰り返している悪手だけが「傾向」。単発のミス指摘は既存の棋譜解析ソフトの仕事。**

②③ のノード化条件は「**同じ特徴グループ・同じ手数帯で N局以上 発生**」。
100局読ませる意味はここにしかない。

③（相手の悪手）は ②（自分の悪手）より価値が高い可能性がある。
「この形にすると相手はよくここで間違える」は勝ちに直結し、`aim` に書く内容そのもの。

### 縦と横の対応

- **④ 相手の戦法** → 兄弟ノード＝ツリーの**横**の広がり
- **①②③ 判断** → その戦法ノードの子＝**縦**の深さ

## 6. キーのバラツキをどう扱うか

1級帯では20手も進めば「全く同じ局面」はまず出ない。
だが **局面同士の距離を測ってファジーにまとめる方式は採らない。**
理由は精度ではなく説明可能性 —— 「なんとなく似た局面」でまとめられても納得できないし、
外れたときに理由が言えない。

代わりに **丸めるのではなく階層化する。**

```
L1: 相手の戦法
L2: + 自分の戦法        ← 自分も常に同じ戦法とは限らないので必須
L3: + 自分の囲い
L4: + 相手の囲い
```

全レベルで同時に集計し、**母数が閾値を超える一番細かいレベルを自動採用**する
（細かい側が2つ以上に割れたときだけ置き換える）。
母数が足りなければ自動的に粗い側へ落ちるので統計が壊れない。

これで「四間飛車には勝てているが、四間飛車＋穴熊には負けている」という
粒度の出し分けが自動で決まる。

- **歩の形は特徴に入れない。** 揺れが最大で、入れた瞬間に全部が「1局」になる。
- **先手／後手は集計軸に入れない。** 母数が半分になる。フィルタで扱う。

## 7. 生成するツリーの抽象度

**1手1ノードは採らない。** 100局から作ると数百ノードになり読めない。
採用するのは **2層構造**。

```
上層＝戦法ノード（④で分岐）… 「相手が四間飛車」「相手が中飛車」   10〜20個
  └ 下層＝判断ノード（①②③で分岐）… その形で繰り返す判断      各3〜7個
       └ 手順は kifu snapshots としてノードの"中"に持つ
```

> **ノードの分岐＝判断の分かれ目。手順はノードの中身。**

手順をノードの中に持つのは既存の範囲切り出し（`handleBranchRangeFromKifu`）が
やっていることそのままなので、ノードモデルの変更は不要。

### 読める上限

**1ツリー 20〜40ノード・深さ3〜4** を目安。

- 1局から作るノードは最大2〜3個（最悪の悪手1つ、最大のチャンス1つ、志向の分岐1つ）
- ノード化には「N局以上で再現」を要求し、単発は捨てる
- 40ノードを超えたら母数の少ない順に切る

「もっと詳しく見たい」は自動生成では解決しない。ノードの中の棋譜を再生して、
気になった局面で自分で範囲切り出しして枝を伸ばす。
**自動生成は骨組みまで、肉付けは人間。**

## 8. 個別に気になっていた点への回答

### 8-1. 自分の戦法も相手によって変える（常に中飛車とは限らない）

**対応済み。**

- 自分の飛車の筋は既に**集計軸 L2**に入っている（`myStrategy`）。
- 「最初に振ったか／早めに振ったか」も判定済み。
  - `swingTiming` … **先発**（自分から決めた）／**対応**（相手を見てから合わせた）
    自分の振りが相手より早い（または相手が振らない）なら先発。
    → 相手の右四間飛車を受けるために6筋へ振る、といったケースを取りこぼさない。
    これはねっこの目的1「相手の呼吸に合わせた方針」の直接の指標になる。
  - `swingSpeed` … 20手目までなら「早い」。**算出・表示済みだが、まだ集計軸ではない。**

### 8-2. 候補手の性質分類（①のため）

「敵陣方向へ動く／駒を取る＝攻め、自玉2マス以内へ動く＝受け、それ以外＝バランス」
という**単発の手の形からの分類は漏れが多い**、という指摘はその通り。

代案：エンジンの読み筋（PV）を使い、**その手を選んだ後の3〜5手**で

- 自分の駒が敵陣に何枚入るか → 攻め
- 自玉周りの守備駒が何枚増えるか → 受け

で測る。手そのものではなく「その手の先にある展開」を見るほうが堅い。
確定は Phase 2 で実データを見てから。

### 8-3. 自動生成でどこまで埋められるか

**確実に埋まる**（特徴抽出と集計だけで足りる）

| 項目 | 根拠 |
|---|---|
| `situation`（相手の戦法） | 特徴抽出そのまま |
| `myApproach`（自分の戦法） | 同上 |
| `usageLevel`（頻度） | 出現局数 → 1〜5 |
| `winRate`（勝率） | 集計値 → 1/3/5/7/9割 |
| `board` / `handSente` / `handGote` | 該当局面そのもの |
| `kifu` / `branchFromMoveIndex` | 区間切り出し |
| `turn`（手番） | 手数の偶奇 |

**ルールで下書きできる**

- `status` … 頻出×低勝率 → `wip`（研究中）
- `label` … 「四間飛車 × 美濃」の機械生成。自然な戦法名は辞書か LLM
- `whenToUse` … 「相手が〇〇のとき」まで

**エンジン導入後に埋まる**

- `evaluation`
- `orientation`（候補手の分類が決まれば）
- `commentTags`（評価値推移から「逆転勝ち／逆転負け」は機械判定できる）

**埋められない ＝ ここがねっこの価値**

`aim`（ここでの狙い）、`caution`（なぜ間違えたか）、`nextStudy`、
`likeLevel`、`memo`、`openingFocus`。

自動値と手入力値の衝突を避けるため、`source: 'auto' | 'manual'` 相当の区別を持たせる。

## 9. 進め方

| Phase | 内容 | 状態 |
|---|---|---|
| 0 | 勝敗・自分の側・対局日のパース、一括取り込み | **完了** |
| 1 | 特徴抽出＋階層集計＋傾向画面（④と戦型別勝率） | **完了** |
| 1.5 | 分岐ノードを分岐手数順に配置する（3章の案A） | 未着手 |
| 2 | エンジン導入 → ①②③ | 未着手 |
| 3 | 2層ツリーの自動生成、LLM による命名 | 未着手 |

Phase 1 まではツリーに一切手を加えない読み取り専用。
ここで傾向抽出が本当に役立つかを確かめてから Phase 2 へ進む。

## 10. まだ決まっていないこと

1. **②③の閾値**（何点落としたら大悪手か）。1級に400点か800点かで出るノードの
   数と質が変わる。実データを流して件数を見てから決める。
2. **候補手の性質分類**（8-2）。Phase 2 で実データを見ながら確定。
3. **最低局数の既定値**（3 / 5 / 10 のどれが読みやすいか）。
4. **囲いテンプレートの精査**。現在16種。相居飛車の細かい囲い（矢倉の発展形など）は
   まだ「その他」に落ちる。
5. **`swingSpeed`（早い／遅い）を集計軸に入れるか。** 入れると母数が半分になる。
